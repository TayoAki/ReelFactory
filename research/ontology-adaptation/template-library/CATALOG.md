# Reference-derived graphic templates

27 source sequences are labelled below. This is a sampled pattern library, not a claim that every cut or animation frame has been exhaustively annotated. Each sequence has eight existing source frames. Teaching reasons and transfer rules are interpretations of those frames and narration.

## 01-icon-map · 8–15s

**Type:** `system-map`

**Teaching job:** Establish how several sources supply a common context hub and a consumer.

**Observed structure:** Source nodes → converging routes → named hub → consumer.

**Retain:** Hub and existing branches stay fixed as additional inputs appear.

**Choose when:** Several distinct inputs contribute to one service or model.

**Consider a different visual when:** A flat list is better when there is no meaningful relationship among items.

**Avoid:** Never imply an integration exists because an icon can be connected.

## 02-white-system · 38–54s

**Type:** `product-mechanism-example`

**Teaching job:** Define a product, connect it to inputs, demonstrate a question, answer and action, then constrain it.

**Observed structure:** Full speaker → product card → compact data/tools diagram → large chat example → governance enclosure.

**Retain:** Same product, question and results carry the explanation forward; presenter remains outside diagram transforms.

**Choose when:** A capability statement needs a concrete worked example.

**Consider a different visual when:** A real UI capture is better when teaching exact interaction steps.

**Avoid:** A suggested action is not proof of executed work.

[Source sample sheet](../graphics-study/02-white-system.jpg)

## 03-layered-cards · 55–81s

**Type:** `product-family`

**Teaching job:** Expand a known product into a family and distinguish the siblings by role.

**Observed structure:** Single card → tilted stack → sibling cards → audience and domain annotations.

**Retain:** Known Genie One card remains central/front; Code left, Agents right.

**Choose when:** Related offerings share a category and have distinct roles.

**Consider a different visual when:** A table is better for many attributes; a tree is better for actual parent/child ownership.

**Avoid:** Stack depth is an editorial family metaphor, not dependency architecture.
